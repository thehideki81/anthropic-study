## Scope & exam weight

This domain covers 18% of scored content.

It covers designing tool interfaces and MCP integrations: differentiating tool descriptions, structured error responses (isError, error categories, retryable), tool distribution across agents, tool_choice configuration, MCP server scoping (.mcp.json vs ~/.claude.json), resources, and built-in tool selection.

The through-line is that tool *description quality* and *deliberate scoping* — not raw tool count — drive reliable agent behavior.

Expect questions that pit a plausible-but-wrong shortcut (force a tool, add more tools, return a generic error) against the documented best practice.

## Task statements

### Task 2.1: Design effective tool interfaces with clear descriptions and boundaries

**What you need to know**

A tool's plaintext `description` is the single highest-leverage factor in how reliably Claude selects and uses it — Anthropic's docs state providing "extremely detailed descriptions" is "by far the most important factor in tool performance."

A good description explains what the tool does, when it should (and should NOT) be used, what each parameter means and how it affects behavior, and any caveats/limitations including what the tool does NOT return; aim for at least 3-4 sentences, more for complex tools. Minimal descriptions (e.g. "Gets the stock price for a ticker.") leave Claude guessing and degrade selection among similar tools.

When two tools overlap in purpose (the classic misrouting failure), the fixes are to consolidate related operations into fewer, more capable tools (one tool with an `action` parameter rather than separate create/review/merge tools), give each tool a clear distinct purpose, rename/namespace tools with service prefixes (e.g. `github_list_prs`, `slack_send_message`), and split generic tools (prefer `search_contacts` over a generic `list_contacts`).

Selection is also steerable through the system prompt and `tool_choice` (though forcing a tool via `tool_choice` is no longer available on every model — see Task 2.3). Selection accuracy degrades notably once you exceed roughly 30-50 tools, which is when namespacing and the tool search tool (with `defer_loading`) become important.

**Key facts**

- Providing extremely detailed tool descriptions is "by far the most important factor in tool performance"; descriptions should cover what the tool does, when it should (and shouldn't) be used, what each parameter means, and caveats/limitations (including what info the tool does NOT return). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Anthropic recommends aiming for at least 3-4 sentences per tool description, more if the tool is complex. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Tool `name` must match the regex `^[a-zA-Z0-9_-]{1,128}$` (1-128 chars of letters, digits, underscore, hyphen). *(Changed: was documented as `{1,64}` in June 2026.)* [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- A user-defined tool definition consists of name, description, input_schema (JSON Schema), and optional input_examples; optional properties available on any tool include `cache_control`, `strict`, `defer_loading`, `allowed_callers` (and `eager_input_streaming` on user-defined tools). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-reference)
- `input_examples` helps with complex/nested/format-sensitive parameters; each example must validate against input_schema (else 400); it is NOT supported on server tools (web search, code execution) or on the computer-use/browser-use client toolsets; cost is ~20–50 tokens per simple example, ~100–200 for complex nested ones. Examples also work with tool search (they expand with the deferred tool's definition). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Best practice: consolidate related operations into fewer tools (e.g. one tool with an `action` param instead of separate create_pr/review_pr/merge_pr) — fewer, more capable tools reduce selection ambiguity. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Use meaningful namespacing: prefix tool names with the service (e.g. github_list_prs, slack_send_message) to make selection unambiguous as the library grows — "especially important when using tool search." [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Define-tools best practices now also say: design tool responses to return only high-signal information — "semantic, stable identifiers (for example, slugs or UUIDs) rather than opaque internal references" and only the fields Claude needs for its next step. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- NEW best practice: "Ask for an explanation, not reasoning" — if a parameter asks Claude why it is making the call, ask for a short explanation or supporting evidence; a parameter that asks for step-by-step reasoning may trigger a `reasoning_extraction` refusal. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Tool selection is steerable via the system prompt: a light instruction like "Use the tools to investigate before responding." increases tool use; "Always call a tool first before responding." pushes further; "Use your judgment about whether to call a tool or respond directly." keeps triggering conservative. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- tool_choice has four options: auto (default when tools provided), any (must use some tool), tool (force a specific named tool), none (default when no tools); with any/tool the API prefills the assistant turn so no natural-language preamble is emitted before tool_use blocks. Forcing (`any`/`tool`) is not supported on every model — see Task 2.3. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Anthropic engineering guidance: give each tool a clear, distinct purpose; prefer purpose-specific tools like search_contacts/message_contact over a generic list_contacts, and use unambiguous parameter names (user_id not user). "Even small refinements to tool descriptions can yield dramatic improvements." Prefix- vs suffix-based namespacing can measurably change eval results, so test the choice. [source](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Tool selection accuracy degrades once you exceed 30-50 available tools; tool search typically loads only the 3-5 tools needed, and both regex and BM25 variants search tool names, descriptions, argument names, and argument descriptions. Each search returns up to 5 tools by default (Claude may set `limit` 1–10,000); up to 10,000 deferred tools per request; at least one tool (normally the search tool) must stay non-deferred; keep your 3–5 most-used tools non-deferred. The tool search tool is listed with no beta header (types `tool_search_tool_regex_20251119` / `tool_search_tool_bm25_20251119`, undated aliases also accepted). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- Docs' rule of thumb for adopting tool search: 10+ tools, tool definitions over 10k tokens, falling selection accuracy, or aggregating multiple MCP servers (200+ tools); standard calling is better below 10 tools. A deferred tool cannot also carry `cache_control` (400). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- MCP spec tool-name guidance: names SHOULD be 1–128 characters, case-sensitive, using A-Z, a-z, 0-9, `_`, `-`, `.`; uniqueness is per server, so clients aggregating multiple servers SHOULD disambiguate (e.g. prefix with a server identifier). [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Both the good and poor tool-description examples on the Define tools page use a get_stock_price tool with a ticker parameter; the terse one ("Gets the stock price for a ticker.") is the docs' explicit example of a poor description. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Tool-use system prompt overhead: Claude Opus 4.8 is 290 tokens (auto/none) vs 410 (any/tool); Claude Opus 5 is 286 vs 406; Claude Opus 5.5 lists 286 for auto/none and no any/tool figure (it doesn't support forced tool use). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)

**Anti-patterns the exam tests**

✅ **Right:** Write detailed descriptions (3-4+ sentences) covering what the tool does, when to use and not use it, each parameter, and limitations; consolidate overlapping tools or give each a distinct, clearly-bounded purpose; namespace tool names; use purpose-specific search_*/message_* tools; recognize that system-prompt wording and tool_choice also steer selection; use namespacing plus the tool search tool / defer_loading at scale; use unambiguous parameter names.

- ❌ Writing terse one-line descriptions (e.g. "Gets the stock price for a ticker.") and relying on the tool name alone — the docs' explicit example of a POOR description, causing unreliable selection among similar tools.
- ❌ Creating many fine-grained tools with overlapping scope (analyze_content AND analyze_document, or separate create_pr/review_pr/merge_pr) instead of consolidating or giving each a distinct, clearly-bounded purpose.
- ❌ Leaving tool names un-namespaced so two services' tools collide as the library grows.
- ❌ Using a generic list_* tool that dumps everything into context instead of a purpose-specific search_*/message_* tool.
- ❌ Assuming description text alone governs behavior while ignoring that system-prompt wording and tool_choice also steer selection.
- ❌ Loading 50+ full tool definitions into context upfront instead of using namespacing plus the tool search tool / defer_loading.
- ❌ Deferring every tool, including the tool search tool itself (400: "At least one tool must have defer_loading=false").
- ❌ Ambiguous parameter names (user instead of user_id).
- ❌ Adding a parameter that asks Claude for its step-by-step reasoning (risks a `reasoning_extraction` refusal) instead of a short explanation/evidence field.
- ❌ Forcing a specific tool with tool_choice:tool when the real fix is a clearer description and distinct boundaries (and on Opus 5.5 / Sonnet 5.5 / Fable 5.1 / Mythos 5.1 forcing returns a 400 anyway).

**Self-check (original, concept-based)**

- **Q:** Two tools, analyze_content and analyze_document, are frequently misrouted. Name two design fixes from Anthropic's guidance.
  **A:** Consolidate them into one tool with an action/type parameter (or eliminate the overlap), and/or rename to give each a clear distinct purpose and namespace; rewrite each description to state precisely when it should and should NOT be used and what input format each expects.
- **Q:** Per Anthropic's docs, what is "by far the most important factor in tool performance," and roughly how long should a description be?
  **A:** Providing extremely detailed tool descriptions; aim for at least 3-4 sentences (more for complex tools), covering what it does, when to use/not use it, each parameter's meaning, and limitations.
- **Q:** Claude isn't calling a tool you expect it to use, even though the description is good. Name two non-description levers.
  **A:** Add keyword-sensitive system-prompt instructions (e.g. "Use the tools to investigate before responding" or the stronger "Always call a tool first"), and — on models that support forced tool use — set tool_choice to any or to the specific tool. On models that reject forcing (e.g. Opus 5.5), rely on prompting with `auto`.
- **Q:** Why does namespacing tool names (e.g. github_list_prs) matter, and when does it become critical?
  **A:** It makes tool selection unambiguous as the library grows; it becomes especially important past ~30-50 tools and when using the tool search tool, which searches names/descriptions/argument names (a shared `github_` prefix lets one search match the whole group).
- **Q:** You have 400 tools across five MCP-backed services and the tool search tool enabled. Which tools should you leave non-deferred, and what must never be deferred?
  **A:** Keep the 3–5 most frequently used tools non-deferred so Claude can call them without searching; never set `defer_loading: true` on the tool search tool itself (at least one tool must remain non-deferred or the request fails with a 400).

### Task 2.2: Implement structured error responses for MCP tools

**What you need to know**

MCP tools report failures in two distinct ways: protocol-level (JSON-RPC) errors for problems with the request structure itself — unknown tool, a request that fails the CallToolRequest schema, server errors — and tool-execution errors, which are returned as a normal successful JSON-RPC result whose body carries `isError: true` plus a `content` array describing what went wrong. Under the current spec revision (2026-07-28), **input-validation errors** (e.g. a date in the wrong format, a value out of range) are explicitly tool-execution errors, because they carry "actionable feedback that language models can use to self-correct and retry with adjusted parameters."

The critical design point is that execution errors must flow back to the model inside the tool result: the spec says clients SHOULD provide tool execution errors to the language model, while they only MAY provide protocol errors (which are "less likely to result in successful recovery"). Don't rely on a JSON-RPC `error` object reaching the model. In the Claude Messages API the equivalent is a `tool_result` content block carrying `is_error: true` and a `content` string.

A uniform "Operation failed" message is an anti-pattern: write instructive, actionable error messages (e.g., "Rate limit exceeded. Retry after 60 seconds.") and prompt-engineer error responses that steer the agent toward correct, more efficient strategies. Mature designs classify failures (transient/timeout, validation/bad-input, business/policy, permission) and attach structured metadata — an error category and a retryable/non-retryable signal — so the agent does not waste retries on permanently-failing calls.

In multi-agent setups, subagents should attempt local recovery within their isolated context and propagate only unresolvable errors up to the parent (which receives only the subagent's final report). Finally, distinguish a genuine access/permission failure (which IS an error) from a valid empty result (a successful query that legitimately returned nothing — not an error). Anthropic's own server tools model this: a web search or tool search that matches nothing returns an empty result list, not an error.

**Key facts**

- The current MCP specification revision is **2026-07-28** (previous: 2025-11-25, 2025-06-18). [source](https://modelcontextprotocol.io/specification/versioning)
- MCP tools use two error-reporting mechanisms: Protocol Errors (standard JSON-RPC errors: unknown tool, malformed requests that fail the CallToolRequest schema, server errors) and Tool Execution Errors reported inside the tool result with `isError: true` (API failures, **input validation errors**, business logic errors). *(Changed: the 2025-06-18 text listed "invalid arguments" under protocol errors.)* [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Clients SHOULD provide tool execution errors to language models to enable self-correction; clients MAY provide protocol errors to language models, though these are less likely to result in successful recovery. [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- An MCP tool execution error is a normal JSON-RPC `result` (not an `error`) containing a `content` array and `isError: true` (the spec's example: "Invalid departure date: must be in the future…"); the spec's example protocol error instead uses the JSON-RPC `error` object with code -32602 and message "Unknown tool: invalid_tool_name". In 2026-07-28 examples, results also carry `"resultType": "complete"`. [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- A successful MCP tool result has shape `{ "content": [ {"type":"text","text":"..."} ], "isError": false }`; content items can be type text, image, audio, resource_link, or embedded resource. Structured output goes in a separate `structuredContent` field — now any JSON value (object, array, string, number, boolean, null) — which must conform to the tool's `outputSchema` if one is declared (servers MUST conform; clients SHOULD validate); for backwards compatibility a tool returning structured content SHOULD also return the serialized JSON in a text block. [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- In the Claude Messages API, you report a tool failure with a `tool_result` block: `{ "type":"tool_result", "tool_use_id":"...", "content":"...", "is_error": true }`; `tool_use_id` is required, `content` and `is_error` are optional (content may be a string or a list of text/image/document/search_result blocks). A response containing tool calls has `stop_reason: "tool_use"`, and tool_result blocks must come FIRST in the user message's content array. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- Anthropic explicitly advises writing instructive error messages — instead of a generic "failed", include what went wrong and what Claude should try next, e.g. "Rate limit exceeded. Retry after 60 seconds." [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- If a tool request is invalid or missing parameters, Claude will retry 2-3 times with corrections before apologizing to the user; you can return is_error:true with a message like "Error: Missing required 'location' parameter". To eliminate invalid calls entirely, use strict tool use (`strict: true`). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- When running parallel calls, if you choose not to execute one (e.g. an earlier call in a sequential batch failed), still return a `tool_result` for it with `is_error: true` and a brief explanation such as "Not executed: the preceding write_file call failed." [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)
- For server tools (e.g. web search) Claude transparently handles errors and you do NOT need to handle is_error results; errors come back inside a 200 response as a `web_search_tool_result_error` block. Current web search error codes: `too_many_requests`, `invalid_tool_input`, `max_uses_exceeded`, `query_too_long`, `request_too_large`, `unavailable`. A search that succeeds but matches nothing returns an empty `content` list, not an error. *(Changed: `invalid_input` → `invalid_tool_input`, `request_too_large` added; the Handle-tool-calls page still shows the older list.)* [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)
- Anthropic's tool-design guidance: prompt-engineer error responses to communicate specific, actionable improvements rather than opaque error codes or tracebacks, and expose a `response_format` enum (concise vs detailed) so the agent can choose token efficiency (concise ~1/3 the tokens of detailed). [source](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Tool responses should return only high-signal information and avoid low-level technical identifiers (uuid, mime_type, 256px_image_url); natural-language or 0-indexed IDs improve Claude's precision over cryptic UUIDs. (Note the API docs frame the same idea as "semantic, stable identifiers… rather than opaque internal references.") [source](https://www.anthropic.com/engineering/writing-tools-for-agents)
- For structured errors, the guide names application-level fields to put INSIDE the tool-result content the agent reads: an `errorCategory` (transient / validation / permission / business), an `isRetryable` boolean, and a human-readable message. These are payload fields YOU design, distinct from the MCP protocol's `isError` flag — they are not part of the MCP spec; the spec only standardizes `isError`. [guide-specific]
- MCP security considerations: servers MUST validate all tool inputs, implement access controls, rate limit invocations, and sanitize outputs; clients SHOULD validate tool results before passing them to the LLM, implement timeouts for tool calls, prompt for confirmation on sensitive operations, and log tool usage. [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- NEW (spec guidance on stateful tools): a call against an expired or unknown state handle "should return a tool execution error that says so, so the model can recover by creating a new one." [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- NEW (2026-07-28): a server MAY answer `tools/call` with an `InputRequiredResult` (`resultType: "input_required"`, e.g. an `elicitation/create` form request) instead of failing; the client retries with `inputResponses` — a non-error path for "I need more information." [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Subagents run in isolated context; only the subagent's final message returns to the parent (not its intermediate tool calls/results) — supporting local recovery in the subagent and propagation of only unresolvable results. The parent may summarize that report; since Claude Code v2.1.210 the final message is scanned for instruction-shaped patterns (control tags are neutralized, text is never removed). An API error that ends a subagent early is never delivered as its result. Invocation tool: `Agent` in tool_use blocks (it still appears as `Task` in the `system:init` tools list; before v2.1.63 tool_use blocks also said `Task` — match both). [source](https://code.claude.com/docs/en/agent-sdk/subagents)
- On the MCP side, outputSchema conformance is stated for structured results; the spec does not state that error results (isError: true) must conform to outputSchema — error content is returned as unstructured content. (reconfirm — not re-verified 2026-10-16; the 2026-07-28 text neither requires nor explicitly exempts error results) [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

**Anti-patterns the exam tests**

✅ **Right:** Return execution failures — including input-validation failures — as a result with `isError: true` (so the model can see and recover from them); write actionable, human-readable error messages with next-step guidance; keep a valid empty result non-error and an access/permission failure as an error; classify failures and attach retryability metadata so the agent retries only recoverable (transient/timeout) calls; have subagents attempt local recovery and surface only unresolvable failures.

- ❌ Returning a uniform "Operation failed" / generic "failed" string for every failure — strips the model of any signal needed to recover.
- ❌ Reporting tool-execution failures as a JSON-RPC `error` object (or otherwise hiding them from the model) instead of a result with `isError: true` — clients are only permitted (MAY), not expected, to surface protocol errors to the model, so recovery becomes unlikely.
- ❌ Returning a bad-argument / out-of-range input as JSON-RPC -32602 — the current spec makes input-validation failures tool execution errors so the model can fix its arguments and retry.
- ❌ Treating a valid empty result as an error by setting isError/is_error — or, conversely, returning an access/permission failure as if it were an empty success.
- ❌ Dumping raw stack traces, tracebacks, or opaque numeric error codes/UUIDs into the error content instead of an actionable, human-readable description.
- ❌ Omitting retryability metadata so the agent retries a permanently-failing (validation/permission/business) error — or marking a transient timeout as non-retryable so a recoverable call is abandoned.
- ❌ Returning a business-rule denial (e.g. a refund exceeding policy) as a bare `isRetryable:false` with no explanation — pair `retriable:false` (`isRetryable:false`) WITH a customer-friendly reason ("This refund exceeds the $200 self-serve limit; a manager must approve it") so the agent communicates the denial to the user instead of retrying or stalling.
- ❌ Having every subagent propagate every low-level error straight to the parent instead of attempting local recovery and surfacing only unresolvable failures.
- ❌ Relying on the LLM to guess because the error lacked next-step guidance.
- ❌ Silently skipping one of several parallel tool calls without returning a `tool_result` (with `is_error: true`) for it.

**Self-check (original, concept-based)**

- **Q:** Why must an MCP tool that hits an API failure return a result with isError:true rather than a JSON-RPC error object?
  **A:** The spec says clients SHOULD pass tool execution errors (isError:true + descriptive content) to the model so it can self-correct, while protocol (JSON-RPC) errors are only MAY-surface and handled mostly at the client layer. Putting execution failures in the tool result lets the model see what happened and attempt recovery or adapt its plan.
- **Q:** An agent calls a tool that validates input and rejects a malformed argument. How should the server report it, should it be flagged retryable, and what should the message contain?
  **A:** Under the current MCP spec it is a tool execution error (result with isError:true), not a JSON-RPC protocol error. It is non-retryable *as-is* — retrying the same input fails identically — so the message should state specifically what was wrong and how to fix it, so the agent changes its input rather than blindly retrying.
- **Q:** How does a "valid empty result" differ from an "access failure," and why does the distinction matter for the isError flag?
  **A:** A valid empty result is a successful operation that legitimately returned no data (isError stays false); an access/permission failure means the operation could not complete (isError true). Conflating them either makes the agent retry normal emptiness or silently accept a permission denial as "nothing found".
- **Q:** In a subagent architecture, what is the recommended error-propagation discipline?
  **A:** Subagents attempt local recovery within their isolated context and propagate only unresolvable errors upward. The parent receives only the subagent's final report as the Agent tool result, so low-level transient noise should be resolved locally rather than polluting the parent's context.
- **Q:** Inside the tool-result content an agent reads, what application-level fields does the guide recommend for a structured error — a bare HTTP status code, a JSON-RPC `error.code`, or something else?
  **A:** Return application-level payload fields: an `errorCategory` (transient / validation / permission / business), an `isRetryable` boolean, and a human-readable message. A bare HTTP status code or a JSON-RPC `error.code` gives the model little to act on (and a JSON-RPC `error` may never be surfaced to it); these named fields are ones you design in the result payload, distinct from — and not part of the same MCP spec as — the protocol's `isError` flag.

### Task 2.3: Distribute tools appropriately across agents and configure tool choice

**What you need to know**

Two related skills sit under this task: deciding which tools each agent gets, and controlling whether/which tool Claude calls via `tool_choice`.

On distribution, Anthropic's guidance is quality over quantity: a small set of thoughtful, consolidated tools selects more reliably than a sprawling library, because "too many tools or overlapping tools can also distract agents from pursuing efficient strategies." Practically, consolidate related operations into fewer capable tools, use service/resource namespacing (`asana_search`, `jira_search`) to disambiguate, and scope each subagent to only the tools it needs (least privilege) via the Agent SDK `AgentDefinition.tools` allow-list (or `disallowedTools` to subtract; if both are set, `disallowedTools` wins) — a read-only reviewer gets just `Read`/`Grep`/`Glob`, never `Edit`/`Bash`. A further distribution lever is the constrained-alternative pattern: when an agent only ever needs a narrow capability, replace a broad capability-heavy tool with a narrower purpose-locked one to shrink the misuse surface — the guide's worked example swaps a generic `fetch_url` (fetches any URL) for a `load_document` that only accepts and validates document URLs, so the agent simply cannot reach unrelated endpoints.

On tool_choice, the Messages API offers exactly four options — `{"type":"auto"}` (default when tools present; Claude decides per turn), `{"type":"any"}` (must call some tool, no text), `{"type":"tool","name":"..."}` (forces that specific tool), and `{"type":"none"}` (no tools; default when no tools). With `any` or `tool` the API prefills the assistant turn so Claude emits no preamble, and a forced call skips thinking. **Forcing is now model- and setting-dependent:** `any`/`tool` error with manual extended thinking (`thinking: {type: "enabled"}`), and Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 reject `any`/`tool` outright (400) — there, use `auto` (plus prompting) with strict tool use, or structured outputs. Parallel calls can be capped with `disable_parallel_tool_use:true`.

**Key facts**

- tool_choice has exactly four options: auto (default when tools are provided; Claude decides whether to call a tool), any (must use one of the provided tools, not a particular one), tool (forces a specific named tool), and none (prevents tool use; default when no tools are provided). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Schemas: forcing a specific tool is `{"type":"tool","name":"get_weather"}`; any is `{"type":"any"}`; auto is `{"type":"auto"}`; none is `{"type":"none"}`. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- NEW — forced tool use is not universal: on Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1 and Claude Mythos 5.1, `any` and `tool` return a 400 error; the documented alternative is `auto` with strict tool use (schema-valid inputs) or structured outputs (fixed JSON shape); `none` still works and prompting still influences which tool `auto` picks. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- When tool_choice is `any` or `tool`, the API prefills the assistant message to force a tool call, so the model will NOT emit any natural-language text/explanation before the tool_use block, even if asked. Forcing also skips thinking on every model that accepts it (the response starts with tool_use, no thinking block). To get narration or thinking plus a tool call, use `auto` plus an explicit instruction in the user message. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- With manual extended thinking (`thinking: {type: "enabled"}`), only `tool_choice` `auto` and `none` are supported; `any` and `tool` produce an error. Adaptive thinking itself doesn't block forced tool use on models that accept forcing (e.g. Claude Opus 5, Claude Haiku 5.5), but the forced call skips thinking. *(Refined: June doc said "extended thinking" generically.)* [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- On models that support forced tool use, combining `tool_choice:{"type":"any"}` with strict tool use (`strict:true` on tool defs) guarantees both that some tool is called AND that inputs match the schema. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- Strict tool use (`strict: true`) uses grammar-constrained sampling to guarantee tool `input` follows `input_schema` and the tool `name` is valid. Limits per request: 20 strict tools, 24 optional parameters total and 16 union-type parameters total across strict schemas; unsupported schema features (recursive schemas, numeric `minimum`/`maximum`, string `minLength`/`maxLength`, `additionalProperties` other than `false`) return a 400; compiled grammars are cached 24 h from last use. Not accepted on `mcp_toolset` or the computer-use/browser-use toolsets. [source](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)
- Parallel tool use is ON by default. Set `disable_parallel_tool_use=true` (a field inside the tool_choice object, not a top-level parameter) with `auto` to ensure AT MOST one tool, or with `any`/`tool` to ensure EXACTLY one tool (where those types are supported). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)
- Anthropic's engineering guidance: "Too many tools or overlapping tools can also distract agents from pursuing efficient strategies"; build a few thoughtful tools for high-impact workflows and scale from there. [source](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Agent SDK AgentDefinition supports per-agent tool scoping: `tools` (string array of allowed tool names; if omitted, inherits every tool available to subagents) and `disallowedTools` (names to remove; also accepts `mcp__server`, `mcp__server__*`, or `mcp__*` patterns). If both are set, `disallowedTools` takes precedence. Other fields include `description` (required), `prompt` (required), `model`, `skills`, `mcpServers`, `maxTurns`, `permissionMode`. A tool left out of `tools` isn't in the subagent's session at all. [source](https://code.claude.com/docs/en/agent-sdk/subagents)
- Constrained-alternative pattern: when an agent only needs a narrow capability, replace a broad capability-heavy tool with a narrower purpose-locked one to shrink the capability/misuse surface — the guide's worked example replaces a generic `fetch_url` (fetches arbitrary URLs) with a `load_document` that only accepts and validates document URLs. The fix is removing the broad tool, not adding description text or forcing the narrow tool with tool_choice. [guide-specific]
- The four documented subagent benefits are context isolation, parallelization, specialized instructions and knowledge, and tool restrictions; each non-fork subagent starts a fresh conversation and only its final message returns to the parent. Subagents can spawn their own subagents (defaults: depth 3 via `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, 20 concurrent via `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`). [source](https://code.claude.com/docs/en/agent-sdk/subagents)
- Documented common tool combinations: read-only analysis = Read/Grep/Glob; test execution = Bash/Read/Grep; code modification = Read/Edit/Write/Grep/Glob; full access = omit the tools field. [source](https://code.claude.com/docs/en/agent-sdk/subagents)
- Subagents are invoked via the Agent tool; include `Agent` in allowedTools to auto-approve invocations. It appears as `"Agent"` in tool_use blocks but as `"Task"` in the system:init tools list (pre-v2.1.63 tool_use blocks also said `Task`) — check both names. [source](https://code.claude.com/docs/en/agent-sdk/subagents)
- Changing tool_choice invalidates cached message blocks under prompt caching (tool definitions and system prompts remain cached, but message content must be reprocessed). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- tool_choice `any`/`tool` cost more in tool-use system-prompt tokens than `auto`/`none` (Claude Opus 4.8: 290 vs 410; Claude Opus 5: 286 vs 406). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- NEW — Programmatic tool calling (GA): adding `allowed_callers: ["code_execution_20260120"]` to a tool lets Claude call it from code inside the code execution container (requires `code_execution_20260120` or later), cutting model round trips and keeping intermediate results out of context. Incompatible with `strict: true`, with forcing via `tool_choice`, and with `disable_parallel_tool_use`; MCP connector tools can't be called programmatically. `allowed_callers` is guidance, not a security boundary. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)

### Task 2.4: Integrate MCP servers into Claude Code and agent workflows

**What you need to know**

Claude Code connects to external tools and data through MCP servers, configured at three scopes that control where the server loads and whether it is shared. Project scope lives in a version-controlled `.mcp.json` at the project root and is the choice for shared team tooling; local scope (the default) and user scope both live in `~/.claude.json`, with local being per-project-private and user spanning all your projects.

`.mcp.json` supports environment variable expansion (`${VAR}` and `${VAR:-default}`) in command, args, env, url, and headers fields, so secrets like API tokens are referenced rather than committed.

Once connected, servers' tools are discovered at connection time; with the default MCP Tool Search, only tool names and server instructions load up front and full schemas are fetched on demand. MCP resources expose read-only content catalogs (issue summaries, doc trees, DB schemas) that you @-mention (`@server:protocol://path`), letting Claude pull context directly instead of making many exploratory tool calls.

Because Claude chooses tools largely from their descriptions, write detailed MCP tool/server descriptions (with critical words near the start — Claude Code cuts long ones) and use service namespacing so the agent reaches for the right MCP tool instead of defaulting to built-in search; and prefer reviewed Directory servers for standard integrations rather than rebuilding them. Outside Claude Code, the Messages API's MCP connector (beta) connects to remote MCP servers directly — tools only.

**Key facts**

- MCP servers have three installation scopes: local (default; current project only; not shared; stored in ~/.claude.json), project (current project only; shared via version control; stored in .mcp.json at project root), and user (all your projects; not shared; stored in ~/.claude.json). Local-scoped MCP servers are stored in `~/.claude.json`, not `.claude/settings.local.json`. [source](https://code.claude.com/docs/en/mcp)
- Older versions called local "project" and user "global". (reconfirm — not re-verified 2026-10-16) [source](https://code.claude.com/docs/en/mcp)
- Use `claude mcp add --scope <local|project|user>` (`-s`) and `--transport <http|sse|stdio>`; `--env`/`-e KEY=value` and `--header`/`-H` set env vars and request headers. For stdio, `--` separates Claude's options from the server command and its args ("Everything after `--` is passed to the server untouched"). WebSocket (`ws`) servers are added with `claude mcp add-json`. [source](https://code.claude.com/docs/en/mcp)
- `.mcp.json` uses a top-level `mcpServers` object; entries can include type, command, args, env, url, headers, headersHelper, timeout, oauth, and alwaysLoad. `type` values: stdio, http, sse, ws; `streamable-http` is accepted as an alias for `http`. An entry with a `url` but no `type` is a configuration error (read as stdio and skipped). [source](https://code.claude.com/docs/en/mcp)
- `.mcp.json` env var expansion supports `${VAR}` and `${VAR:-default}`, valid in command, args, env, url, and headers. If a variable is unset with no default, the config still loads: Claude Code shows a missing-variable warning in `claude mcp list` and `/mcp` and uses the literal `${VAR}` text. *(Changed: June doc said Claude Code "fails to parse the config".)* In a remote server's url/headers, credential variables such as `ANTHROPIC_API_KEY` expand as empty. [source](https://code.claude.com/docs/en/mcp)
- Project-scoped servers from .mcp.json require approval before use in interactive sessions; reset with `claude mcp reset-project-choices`. In `claude -p`, Agent SDK and cloud sessions Claude Code can't prompt, so it loads them without asking — block with `disabledMcpjsonServers` or use `--strict-mcp-config` with `--mcp-config`. [source](https://code.claude.com/docs/en/mcp)
- Scope precedence (highest first): local, project, user, plugin-provided, then claude.ai connectors; organization-provided `managedMcpServers` (v2.1.259+) rank above all of these. When the same server is defined in multiple places, the whole entry from the highest-precedence source is used; fields are NOT merged across scopes. [source](https://code.claude.com/docs/en/mcp)
- HTTP is the recommended transport for remote servers; "The SSE (Server-Sent Events) transport is deprecated. Use HTTP servers instead, where available." (Claude Code v2.1.265+ tries HTTP first and falls back to SSE automatically.) Remote servers requiring auth use OAuth, completed via `/mcp` (or `claude mcp login <name>`). [source](https://code.claude.com/docs/en/mcp)
- MCP resources are referenced with @-mentions using the format `@server:protocol://resource/path` (e.g., `@github:issue://123`, `@postgres:schema://users`); they are fetched automatically and attached, and Claude Code auto-provides tools to list and read resources (`ListMcpResourcesTool`, `ReadMcpResourceTool`) when servers support them. [source](https://code.claude.com/docs/en/mcp)
- MCP resources let servers share data that provides context to models (files, DB schemas, application-specific info); each resource is identified by a URI and resources are application-driven (the host decides how to include them), distinct from model-controlled tools. Servers MUST return JSON-RPC -32602 for a non-existent resource (not an empty `contents` array). [source](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- Detailed tool descriptions are "by far the most important factor in tool performance"; aim for at least 3-4 sentences, more for complex tools, and use meaningful namespacing in tool names so the agent reaches for the right MCP tool. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- MCP Tool Search is enabled by default: only tool names and server instructions load at session start, and full tool definitions are deferred and fetched on demand via the `ToolSearch` tool (disable via `permissions.deny: ["ToolSearch"]` or `ENABLE_TOOL_SEARCH=false`; `ENABLE_TOOL_SEARCH` accepts unset/true/auto/auto:N/false, where auto defers once definitions reach 10% of the context window). Tool search is off by default when `ANTHROPIC_BASE_URL` points to a non-first-party host. [source](https://code.claude.com/docs/en/mcp)
- Claude Code cuts MCP server instructions and the description of a tool that loads upfront at 4,096 characters, and the description of a tool loaded via tool search at 16,384 characters (override with `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH`) — put critical details and search keywords near the start. *(Changed: June doc said 2 KB each; the 2,048 limit applied before v2.1.296.)* [source](https://code.claude.com/docs/en/mcp)
- `alwaysLoad: true` on a server (available on all server types) loads all its tools upfront regardless of `ENABLE_TOOL_SEARCH`, and startup waits for that server (capped at the 5-second connect timeout); `alwaysLoad: false` keeps all its tools deferred (v2.1.287+). Server authors can set `_meta["anthropic/alwaysLoad"]` per tool. The June note that `alwaysLoad` requires v2.1.121+ is no longer stated (reconfirm — not re-verified 2026-10-16). [source](https://code.claude.com/docs/en/mcp)
- Claude Code warns when MCP tool output exceeds 10,000 tokens; the default maximum is 25,000 tokens, adjustable via `MAX_MCP_OUTPUT_TOKENS`. Over-limit successful results without images are saved to a file and Claude gets the path; text results over 50,000 characters are persisted to disk unless the tool declares `_meta["anthropic/maxResultSizeChars"]` (ceiling 500,000). [source](https://code.claude.com/docs/en/mcp)
- MCP tools are named `mcp__<server>__<tool>`; Claude Code leaves out any MCP tool whose full name exceeds 128 characters. Plugin MCP tools are callable as `mcp__plugin_<plugin-name>_<server-name>__<tool-name>` (non-alphanumeric chars replaced by `_`), so a hook matcher like `mcp__database-tools__.*` won't match a plugin-bundled server. [source](https://code.claude.com/docs/en/mcp)
- MCP permission rules: `mcp__puppeteer` or `mcp__puppeteer__*` match every tool from that server; `mcp__puppeteer__puppeteer_navigate` matches one tool; allow-rule globs are honored only after a literal `mcp__<server>__` prefix. [source](https://code.claude.com/docs/en/permissions)
- NEW: MCP prompts become commands, run as `/mcp__servername__promptname` (listed as `/servername:promptname (MCP)`); MCP elicitation (form mode and URL mode) shows an interactive dialog automatically; a server can force a permission prompt on every call with `_meta["anthropic/requiresUserInteraction"]: true`. [source](https://code.claude.com/docs/en/mcp)
- MCP connector (Messages API): beta, header `mcp-client-2025-11-20` (the older `mcp-client-2025-04-04` is deprecated; `mcp-client-2026-09-15` adds tool-list pinning). Only MCP tool calls are supported (not resources/prompts); servers must be publicly exposed over HTTP (Streamable HTTP or SSE) — local stdio servers can't be connected. Servers go in `mcp_servers`; an `mcp_toolset` entry in `tools` configures them via `default_config`/`configs` (`enabled`, `defer_loading`) for allowlists/denylists; results come back as `mcp_tool_result` blocks with `is_error`. [source](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)
- MCP spec deprecations (2026-07-28 registry): the HTTP+SSE transport (migrate to Streamable HTTP), plus Roots, Sampling, Logging and Dynamic Client Registration are Deprecated (earliest removal in a revision on/after 2027-07-28). [source](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)

### Task 2.5: Select and apply built-in tools (Read, Write, Edit, Bash, Grep, Glob) effectively

**What you need to know**

Claude Code (and the Agent SDK, which shares the same tools, agent loop, and context management) exposes a set of built-in tools whose names are the exact strings used in permission rules, subagent `tools` lists, and hook matchers.

The five tools split by job:

1. Grep searches file *contents* (regex over lines — function names, error strings, imports, exported symbols).
2. Glob matches file *paths* by name pattern (`**/*.test.tsx`).
3. Read returns a file's contents with line numbers.
4. Write creates or fully overwrites a file.
5. Edit does exact-string replacement of one `old_string` with one `new_string`.

Edit enforces three checks — read-before-edit, exact match, and uniqueness — so when `old_string` is non-unique you either add surrounding context to pin one occurrence or set `replace_all: true`. (On newer models, Claude Code relaxes read-before-edit when reading the file wouldn't need a permission prompt.)

The effective workflow is incremental: start with Grep/Glob (or their Bash equivalents) to find entry points and exported names, Read only the files that matter, follow imports outward — rather than reading every file upfront, which wastes context. Read-only tools (Read, Grep, Glob) require no permission inside the working directory and respect Read deny rules; Write/Edit (and Bash) are gated and respect Edit deny rules.

**Platform note (new since June 2026):** on macOS, Linux and WSL, Claude Code now leaves `Glob` and `Grep` *out of the default tool set*; Claude searches with `find`/`grep` through Bash (embedded `bfs`/`ugrep`), and those searches hit your hooks/permission rules as `Bash` calls. Glob/Grep come back when you name them in `--tools`/`--allowedTools` (or the SDK equivalents), when Bash is removed from the session, or for a subagent that lists them and omits Bash. On Windows they remain default. The content-vs-path distinction below is unchanged.

**Key facts**

- Tool names are exact strings reused across permission rules, subagent tool lists, and hook matchers. The built-in set includes Read, Write, Edit, Bash, Grep, Glob (plus Agent, WebFetch, WebSearch, NotebookEdit, LSP, Monitor, Skill, ToolSearch, AskUserQuestion, PowerShell, Workflow, etc.). [source](https://code.claude.com/docs/en/tools-reference)
- NEW: Glob and Grep are absent by default on macOS, Linux and WSL (Claude uses `find`/`grep` via Bash); they are restored by naming them in `--tools`/`--allowedTools` or SDK options, by removing Bash (deny rule, `--disallowedTools`, `--restricted`), or per subagent when its `tools` lists Glob/Grep and leaves out Bash. A settings-file allow rule does not restore them. [source](https://code.claude.com/docs/en/tools-reference)
- Permission required by tool (Manual mode, paths inside the working directory): Read No, Grep No, Glob No, LSP No, Agent No, AskUserQuestion No, ToolSearch No; Edit Yes, Write Yes, Bash Yes, NotebookEdit Yes, Monitor Yes, WebFetch Yes, WebSearch Yes, Skill Yes, ExitPlanMode Yes. Read/Grep/Glob still prompt for paths outside the working/additional directories, and Bash runs a built-in set of read-only commands without prompting. [source](https://code.claude.com/docs/en/tools-reference)
- Grep searches file contents (lines) and is built on ripgrep, using ripgrep regex (NOT POSIX), so metacharacters need escaping (e.g. `interface\{\}`); a pattern ripgrep rejects returns an error with ripgrep's diagnostic (v2.1.208+). Glob finds files by name pattern. [source](https://code.claude.com/docs/en/tools-reference)
- Grep output_mode has three values: `files_with_matches` (paths only, the DEFAULT), `content` (matching lines with file+line number), and `count` (matches per file, plus a total). Scope with `glob` (e.g. `**/*.tsx`) or `type` (e.g. `py`, `rust`); `multiline: true` matches across line boundaries. [source](https://code.claude.com/docs/en/tools-reference)
- Grep respects .gitignore (skips ignored files unless a path is passed directly). Glob does NOT respect .gitignore by default; set CLAUDE_CODE_GLOB_NO_IGNORE=false to make Glob respect it. [source](https://code.claude.com/docs/en/tools-reference)
- Glob supports `**` recursive matching, sorts results by modification time, and caps at 100 files (a truncation flag is returned when the cap is hit). [source](https://code.claude.com/docs/en/tools-reference)
- Edit performs EXACT string replacement (no regex, no fuzzy match) and must pass three checks: read-before-edit, exact match of old_string, and uniqueness (old_string appears exactly once). A path matched by a `Read` deny rule is refused before any of these (v2.1.208+). [source](https://code.claude.com/docs/en/tools-reference)
- Read-before-edit nuance (changed, v2.1.208+): Claude Opus 4.6, Claude Haiku 4.5 and older models always require the read; newer models can edit an unread file when reading it wouldn't need a permission prompt and Read is available. A file changed on disk since the last read can still be edited if `old_string` matches the current content exactly and unambiguously; a read cut short with a `PARTIAL view` notice doesn't count. [source](https://code.claude.com/docs/en/tools-reference)
- When old_string is non-unique, Edit's documented resolution is to supply a longer string with enough surrounding context to pin one occurrence, OR set replace_all: true to replace every occurrence. (The syllabus also names Read + Write as the fallback when a targeted Edit can't find a unique match.) [source](https://code.claude.com/docs/en/tools-reference)
- Read returns contents WITH line numbers and uses absolute paths; supports offset and limit. One call returns at most 25,000 tokens by default (`CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS`) and refuses a whole file over 256 KB; a whole-file read over the token limit returns a first page with a PARTIAL view notice; an explicit offset/limit read that still exceeds the limit errors. v2.1.296+ adds `allow_large: true` to read a whole file sized against remaining context. Read handles images, PDFs (over 10 pages read in ranges via a `pages` parameter, up to 20 pages at a time), and .ipynb notebooks. Read does NOT read directories — use ls via Bash. [source](https://code.claude.com/docs/en/tools-reference)
- Write creates or fully overwrites a file (no append/merge). Overwriting an EXISTING file requires a prior read on Claude Opus 4.6, Claude Haiku 4.5 and older models (and for notebooks or partially read files on every model); newer models can overwrite an unread file under the same conditions as read-before-edit (v2.1.228+). Writing a new file never needs a read. For partial changes, use Edit instead of Write. *(Changed: June doc said every overwrite requires a read.)* [source](https://code.claude.com/docs/en/tools-reference)
- Viewing a file via Bash satisfies read-before-edit when the command is `cat`, `nl`, `bat`, `batcat`, `head`, `tail`, `sed -n 'X,Yp'`, `grep`, `egrep`, `fgrep`, or `rg` on a single file with no pipes or redirects (a search that prints no matches doesn't count). *(Expanded list.)* [source](https://code.claude.com/docs/en/tools-reference)
- Permission rule grouping: `Read(...)` covers Read/Grep/Glob/LSP; `Edit(...)` covers Edit/Write/NotebookEdit; an Edit(...) allow rule also grants read access to the same path, and a Read(...) deny rule also blocks Edit/Write on that path. `Bash(npm run *)` patterns apply to Bash and Monitor (`:*` is an equivalent trailing wildcard). Rules evaluate deny → ask → allow; the first match wins regardless of specificity. [source](https://code.claude.com/docs/en/permissions)
- The Agent SDK gives the same built-in tools as Claude Code; pre-approve them via allowedTools (TypeScript) / allowed_tools (Python), e.g. ["Read", "Glob", "Grep"] for a read-only analysis agent (naming Glob/Grep there also restores them on macOS/Linux/WSL). [source](https://code.claude.com/docs/en/agent-sdk/overview)
- Bash default timeout is two minutes (`BASH_DEFAULT_TIMEOUT_MS`), with a ceiling of 10 minutes by default (`BASH_MAX_TIMEOUT_MS`); Claude raises it per call via the `timeout` parameter. Output read-back defaults to 30,000 characters, raisable via BASH_MAX_OUTPUT_LENGTH up to a hard ceiling of 150,000; the `bashOutputMaxChars` setting (v2.1.261+, up to 128,000) sizes the inline ceiling instead. [source](https://code.claude.com/docs/en/tools-reference)

**Anti-patterns the exam tests**

✅ **Right:** Build understanding incrementally (Grep/Glob to find entry points -> Read only what matters -> follow imports); use dedicated search/read capabilities rather than reading everything; reach for Edit for targeted small changes; on a non-unique Edit add surrounding context or use replace_all: true (or fall back to Read + Write for a full rewrite); treat Grep as ripgrep regex (escape `{}`/`()` etc.); remember Grep's default output_mode is files_with_matches (paths only); Read a file before Editing or Writing it; remember Glob does not honor .gitignore by default and Grep skips gitignored files; use ls via Bash to list directories; keep Glob = paths and Grep = contents.

- ❌ Reading every file in the repo upfront to "get full context" instead of building understanding incrementally (Grep/Glob to find entry points -> Read only what matters -> follow imports).
- ❌ Piping `cat`/`grep`/`find` output through Bash as a substitute for Read when you then need to Edit — only single-file views with no pipes or redirects satisfy read-before-edit. (Note: on macOS/Linux/WSL Claude Code now *defaults* to Bash `find`/`grep` for search; the exam's conceptual point — use purpose-built search, not brute-force reading — still holds.)
- ❌ Reaching for Read+Write to make a small change when Edit is the correct targeted tool.
- ❌ Retrying the same non-unique Edit verbatim, instead of adding surrounding context or using replace_all: true.
- ❌ Assuming Grep uses POSIX regex (it uses ripgrep regex, so `{}`/`()` etc. must be escaped).
- ❌ Assuming Grep's default output_mode returns matching lines — it returns files_with_matches (paths only) by default.
- ❌ Trying to Edit or Write a file without having Read it first (strictly required on older models, notebooks and partially read files; good practice everywhere).
- ❌ Expecting Glob to honor .gitignore (it does not by default) or expecting Grep to search gitignored files (it skips them).
- ❌ Using Read to "list a directory" (Read reads files only; use ls via Bash).
- ❌ Treating Glob as a content search or Grep as a filename matcher — Glob = paths, Grep = contents.
- ❌ Expecting a settings-file allow rule for `Grep` to bring the Grep tool back on macOS — only `--tools`/`--allowedTools` (or removing Bash, or a subagent's `tools` list without Bash) restores it.

**Self-check (original, concept-based)**

- **Q:** An Edit fails because old_string appears three times in the file. What are the two documented ways to make it succeed, and which one effectively mirrors a Read + Write rewrite?
  **A:** (1) Provide a longer old_string with enough surrounding context to uniquely pin one occurrence, or (2) set replace_all: true to replace all three. replace_all (rewriting every occurrence at once) is closest to a Read + Write full rewrite when targeted single-match editing is the wrong fit.
- **Q:** You need to find every file that imports a module and then locate the exported symbol's definition. Which tools, in what order, and why not just read all files?
  **A:** Use Grep to search contents for the import string / exported name (output_mode content for lines), optionally Glob to scope by path pattern, then Read only the file(s) that define or use the symbol and follow imports outward. Reading all files upfront wastes context; incremental Grep->Read tracing is the intended pattern.
- **Q:** On a Mac, you define a read-only subagent with `tools: ["Read", "Grep", "Glob"]`, even though Glob and Grep are absent from Claude Code's default tool set there. Will it get them, and why is this a sound least-privilege design?
  **A:** Yes — a subagent that lists Glob/Grep in `tools` and leaves out Bash gets them back for that subagent. It's sound least privilege: the agent can search contents (Grep) and paths (Glob) and read files, but cannot execute shell commands or modify files, and Read/Grep/Glob need no permission prompt inside the working directory.
- **Q:** What is the default output_mode of Grep, and what does a default Glob result give you that Grep's default does not?
  **A:** Grep defaults to files_with_matches (file paths only, no line content). Glob also returns paths but sorted by modification time and capped at 100; to get actual matching lines from Grep you must set output_mode: content.

## Concept glossary (this domain's appendix slice)

- **Tool description** - The detailed plaintext field telling Claude what a tool does, when to use it, and how it behaves — the primary driver of tool selection. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- **input_schema** - A JSON Schema object defining a tool's expected parameters, with per-parameter descriptions. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- **input_examples** - Optional array of schema-valid example inputs that help Claude format complex/nested/format-sensitive tool calls; not supported on server tools or the computer/browser-use toolsets. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- **tool_choice** - Messages API parameter controlling whether and which tool Claude calls: auto (default with tools), any (must use a tool), tool (force a named tool), none (default without tools); any/tool unsupported on some models. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- **auto (tool_choice)** - Default when tools are provided; Claude decides each turn whether to call a tool or answer directly. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- **any (tool_choice)** - Forces Claude to call one of the provided tools (guarantees a tool call, not text) without specifying which; returns 400 on Opus 5.5, Sonnet 5.5, Fable 5.1, Mythos 5.1. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- **tool (forced tool_choice)** - Forces a specific tool via {"type":"tool","name":"..."}; ensures that exact tool runs on models that support forcing (skips thinking). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- **none (tool_choice)** - Prevents any tool use; the default when no tools are provided. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- **disable_parallel_tool_use** - Field inside tool_choice; with auto caps Claude to at most one tool, with any/tool to exactly one tool. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)
- **Strict tool use** - strict:true on a tool definition uses grammar-constrained sampling so tool inputs match the JSON schema exactly; limits 20 strict tools / 24 optional / 16 union params per request; pairs with any (where supported) or auto for valid calls. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use)
- **Namespacing** - Prefixing tool names by service/resource (e.g. github_list_prs) to eliminate selection ambiguity as the tool library grows. [source](https://www.anthropic.com/engineering/writing-tools-for-agents)
- **Tool consolidation** - Grouping related operations into fewer, more capable tools (e.g. one tool with an action param) to reduce selection ambiguity. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)
- **Tool search tool** - Server tool that dynamically discovers and loads only relevant tools (up to 5 per search by default) so selection accuracy stays high beyond ~30-50 tools; variants tool_search_tool_regex_20251119 and tool_search_tool_bm25_20251119 (no beta header). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- **defer_loading** - Tool-definition flag (true) that keeps a tool out of the context prefix until discovered via tool search; the search tool itself must never be deferred; preserves prompt caching. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- **allowed_callers / programmatic tool calling** - Tool property that lets code in the code execution sandbox (`code_execution_20260120`+) call a tool, keeping intermediate results out of context; GA; not a security boundary. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling)
- **isError (MCP)** - Boolean field in an MCP tool result indicating the tool's own execution failed (incl. input validation); the failure is still returned as a successful JSON-RPC result so the model can see it. [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- **is_error (Claude API)** - Optional boolean on a tool_result content block in the Messages API; set true when the client tool's execution resulted in an error. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- **Protocol (JSON-RPC) error** - Standard JSON-RPC error object (e.g. code -32602) for unknown tools, malformed requests, or server errors — distinct from execution errors; clients MAY (not SHOULD) surface it to the model. [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- **Tool execution error** - A failure inside the tool's logic (API failure, input validation error, business-logic violation) returned in the result content with isError:true. [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- **structuredContent** - MCP tool-result field carrying any JSON value that conforms to the tool's declared outputSchema (when present), ideally mirrored as serialized JSON in a text block. [source](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- **tool_result block** - A content block in a Claude user message carrying tool_use_id, optional content, and optional is_error, returned to continue the agentic loop; must precede any text in that message. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- **Transient error** - A temporary failure (timeout, rate limit, service unavailable) that is typically retryable, usually with backoff. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- **Retryable vs non-retryable** - Metadata signaling whether re-invoking the tool with the same call could succeed; transient errors are retryable, validation/permission/business errors generally are not. [source](https://www.anthropic.com/engineering/writing-tools-for-agents)
- **Instructive error message** - An error string that states what went wrong and the next step (e.g. "Retry after 60 seconds"), instead of a generic "failed" or a raw traceback. [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)
- **Valid empty result** - A successful tool operation that legitimately returns no data; not an error and must not set the error flag (e.g. web search with no matches returns an empty list). [source](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool)
- **.mcp.json** - Project-root file (version-controlled) holding project-scoped MCP server config under a top-level mcpServers object; the mechanism for sharing tooling with a team. [source](https://code.claude.com/docs/en/mcp)
- **~/.claude.json** - Home-directory file storing both local-scoped (per-project, private) and user-scoped (all-projects, private) MCP server configurations. [source](https://code.claude.com/docs/en/mcp)
- **MCP installation scope** - local (default, current project, not shared), project (current project, shared via VCS), or user (all your projects, not shared) — set with claude mcp add --scope. [source](https://code.claude.com/docs/en/mcp)
- **Environment variable expansion** - Use of ${VAR} or ${VAR:-default} inside .mcp.json command/args/env/url/headers to inject machine-specific paths and secrets without hardcoding them; unset vars warn rather than fail. [source](https://code.claude.com/docs/en/mcp)
- **MCP resource** - Read-only, URI-addressed, application-driven content a server exposes to provide model context (files, DB schemas, issue summaries); referenced via @server:protocol://path in Claude Code. [source](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)
- **MCP Tool Search** - Default Claude Code behavior that defers full MCP tool schemas, loading only names/server instructions upfront and fetching schemas on demand via the ToolSearch tool to conserve context. [source](https://code.claude.com/docs/en/mcp)
- **alwaysLoad** - .mcp.json per-server boolean that exempts (true) or forces (false) a server's tools from/into tool-search deferral; per-tool `_meta["anthropic/alwaysLoad"]` for server authors. [source](https://code.claude.com/docs/en/mcp)
- **MCP connector** - Messages API beta (`mcp-client-2025-11-20`) that connects to remote HTTP MCP servers via `mcp_servers` + an `mcp_toolset` entry; tools only. [source](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)
- **Anthropic Directory** - Catalog of reviewed MCP connectors (claude.ai/directory) addable with claude mcp add; preferred over building custom servers for standard integrations. [source](https://code.claude.com/docs/en/mcp)
- **Least-privilege tool scoping** - Granting each agent only the tools its role requires, reducing risk and improving selection focus. [source](https://code.claude.com/docs/en/agent-sdk/subagents)
- **AgentDefinition.tools / disallowedTools** - Agent SDK fields that allow-list (tools) or subtract (disallowedTools, which wins if both set) the tool set for a subagent. [source](https://code.claude.com/docs/en/agent-sdk/subagents)
- **Context isolation (subagents)** - Each subagent runs in a fresh conversation; only its final message returns to the parent, keeping the main context lean. [source](https://code.claude.com/docs/en/agent-sdk/subagents)
- **Grep tool** - Content-search tool built on ripgrep; finds lines matching a regex inside files (function names, errors, imports); absent by default on macOS/Linux/WSL. [source](https://code.claude.com/docs/en/tools-reference)
- **Glob tool** - File-path pattern matcher (e.g. **/*.test.tsx) returning matching paths sorted by mtime, capped at 100; absent by default on macOS/Linux/WSL. [source](https://code.claude.com/docs/en/tools-reference)
- **Read tool** - Returns a file's contents with line numbers; paginates large files via offset/limit (25,000-token default per call); handles images, PDFs, notebooks. [source](https://code.claude.com/docs/en/tools-reference)
- **Write tool** - Creates or fully overwrites a file with provided content (no append/merge); overwriting requires a prior read on older models, notebooks, and partially read files. [source](https://code.claude.com/docs/en/tools-reference)
- **Edit tool** - Exact-string replacement of old_string with new_string; requires read-before-edit, exact match, and uniqueness. [source](https://code.claude.com/docs/en/tools-reference)
- **output_mode** - Grep parameter: files_with_matches (default), content, or count, controlling what the search returns. [source](https://code.claude.com/docs/en/tools-reference)
- **replace_all** - Edit parameter; when true, replaces every occurrence of old_string instead of requiring a unique match. [source](https://code.claude.com/docs/en/tools-reference)
- **read-before-edit** - Edit/Write precondition: the file must have been read this conversation before modification (always on Opus 4.6/Haiku 4.5 and older; relaxed on newer models when reading wouldn't need a permission prompt). [source](https://code.claude.com/docs/en/tools-reference)
- **allowedTools** - Agent SDK / CLI option that pre-approves a list of tool names (e.g. Read, Glob, Grep) for an agent. [source](https://code.claude.com/docs/en/agent-sdk/overview)
